# Victron Multiplus/Quattro (ESS external control)

Omnibattery drives a Victron Multiplus or Quattro behind a GX device (Cerbo GX, Venus GX, or Venus OS) through ESS **external control** (Hub-4 Mode 3): it writes the AC power setpoint directly over Modbus TCP instead of relying on the GX device's own self-consumption loop.

!!! warning "Experimental — still pending a live-hardware test"
    Every register this driver reads or writes was checked against `attributes.csv` from the official `victronenergy/dbus_modbustcp` GitHub repository — the actual table Victron's own Modbus-TCP server is generated from — not a secondhand transcription. That still didn't catch everything: a reviewer running read-only checks against their own GX device found two real problems before any control was ever enabled — a wrong consumption register (fixed: see "What you will see" below) and an ESS-mode safety check that would have stayed silently inert on their hardware (fixed: the check now refuses to write whenever it can't positively confirm External control, not just when it can positively confirm the opposite). None of this replaces a live test: start with manual, low-power commands (e.g. +200 W, then -200 W) with the battery otherwise idle, and confirm the grid sensor and battery power move the way you expect before enabling automatic control.

    One behavioural note worth knowing before you start: switching **Settings → ESS → Mode** to **External control** disables Victron's **BatteryLife** feature for as long as external control is active — this is Victron's own documented design, not something Omnibattery does.

## Do I need it?

**Use it if** your Multiplus/Quattro's AC-out carries the house load at the same point your Home Assistant grid sensor measures. The battery's state of charge (SOC) and power come from the GX device's system aggregate, which exists on every installation regardless of whether the battery also answers as its own Modbus service.

**Do not use it if** your installation's topology is different — a Multi that is one of several parallel AC-coupled sources, rather than the single path to the meter, needs a different control mapping than this driver provides.

| Supported equipment | Connection | Automatic control | Important limit |
|---|---|---|---|
| Multiplus/Quattro behind a GX device | Modbus TCP to the GX device (not the Multi directly) | Yes, via ESS external control | Single-phase only; the AC power setpoint must be rewritten at least once every 60 s or the Multi reverts to passthrough — Omnibattery does this automatically. |

Omnibattery reads battery SOC and power from the system aggregate, the power the Multi itself measures on its AC-out (not total house consumption — see below), and the ESS AC power setpoint readback. The AC-out reading matters for correctness, not just display: the setpoint register controls power at the Multi's AC-input, not the battery, so every write adds the current AC-out power to the requested battery power before sending it — without that compensation, a "charge" command could discharge the battery instead whenever there's a load on the output. Because the Multi only remembers the AC-input figure, Omnibattery re-derives and rewrites it every time the AC-out reading changes (about every 2 s), not only when the requested battery power changes. Omnibattery writes the setpoint and the `DisableCharge`/`DisableFeedIn` flags, which it sets together while the battery should be idle.

## Before you start

- Reach the GX device's Modbus TCP server from Home Assistant: **Settings → Services → Modbus/TCP** on the GX device, enabled.
- Find the Multiplus/Quattro (`vebus`) unit id under **Settings → Services → Modbus/TCP → Available services** on the GX device. It is not guessable and varies per installation. The **system unit id** defaults to 100 — Victron's own documented default — and rarely needs changing.
- Set **Settings → ESS → Mode** to **External control** on the GX device. Do this only once you are ready to let Omnibattery drive it — this disables the GX device's own self-consumption loop.
- Decide your charge/discharge power ceiling yourself: unlike most other brands, there is no hardware-reported value to check this against, so enter it deliberately in the wizard.

## How to add it

1. Open **Settings → Devices & services → Add integration** and select **Omnibattery**. For an existing installation, open Omnibattery and select **Configure**.
2. At **Battery _n_ — Brand**, select **Victron Multiplus/Quattro (ESS external control)**.
3. At **Configure battery _n_ — Connection (Victron)**, enter **Name**, the GX device's **IP Address** and **Modbus Port**, the **vebus unit id**, leave **System unit id** at 100 unless you know otherwise, and set your **Max Charge Power** / **Max Discharge Power**.
4. Finish the shared power and SOC limits, including nominal battery capacity — this route does not report it natively.

The wizard confirms both unit ids answer over Modbus; it cannot confirm the register map itself is correct for your Venus OS version.

## What you will see

You will see automatic battery control and the shared manual power controls, plus **ESS Disable Charge** and **ESS Disable Feed-in** switches (they show what you set; Omnibattery additionally sets both flags on the Multi once this battery has been idle for 30 seconds), a **Battery Voltage** sensor, an **ESS AC Power Setpoint** sensor (the raw grid-point register, after AC-out compensation — not the battery power), and two more diagnostic sensors: **AC Output Power** (what the Multi itself measures on its AC-out port, in 10 W steps — negative when something on that side, such as AC-coupled solar or another battery, feeds back into the Multi; deliberately not one of Victron's derived "consumption" figures) and **ESS Control Mode** (reports "External control" only when the GX device's own ESS-mode setting agrees). The device page also shows the GX device's own serial number, when it answers that register.

Once this battery has been commanded to 0 W for 30 seconds — in practice, when Omnibattery is using another battery or nothing needs doing — it is locked idle: Omnibattery sets both disable flags, so the Multi neither charges nor discharges whatever the AC-out power does. The flags return to whatever your switches say with the next non-zero command. Until the 30 seconds are up, a 0 W command just matches import to the AC-out power. Stopping Omnibattery (or losing the connection) releases control after at most 60 seconds, when the Multi's own watchdog reverts it to passthrough; there is currently no confirmed way to restore the GX device's own ESS mode immediately, and BatteryLife stays disabled until you switch ESS Mode back yourself.

Two things make Omnibattery refuse to write a setpoint at all, by design: the **AC Output Power** reading being unavailable (no successful read yet, or none in the last 10 seconds — better to do nothing than send an uncompensated value), and **ESS Control Mode** being anything other than a *positively confirmed* "External control". That second one is deliberately strict: an unreadable or missing mode check refuses exactly like a confirmed-wrong one — a GX device that can't answer this check at all gets no writes, not writes-by-default.

Cell-balance monitoring, voltage taper, and MPPT solar telemetry are not available for this route.

## If it does not work

- Confirm Modbus/TCP is enabled on the GX device and reachable from Home Assistant.
- Re-check the vebus unit id under **Settings → Services → Modbus/TCP → Available services** — it can differ from what another tool or guide assumed. If your GX device's system aggregate does not answer on unit id 100, re-check that value too.
- Confirm **Settings → ESS → Mode** is still **External control**; anything else means the GX device's own loop is driving the Multi, not Omnibattery. The **ESS Control Mode** sensor confirms this directly — and if it's missing entirely, nothing will be written at all, which is the safe failure mode.
- If nothing is being commanded at all, check both **AC Output Power** and **ESS Control Mode** — either one being unavailable or unconfirmed blocks every write by design.
- If the battery SOC or power reading looks wrong, compare against the official Victron GX Home Assistant integration's own sensors for the same battery, if installed.

??? "Technical notes: register map, design decisions, and what caught two real bugs"
    **Register map** (unit ids: the vebus unit id you entered for the Multi; the system unit id, default 100, for the system aggregate and settings service). Every register below is checked against `attributes.csv` from the official `victronenergy/dbus_modbustcp` GitHub repository — the actual table Victron's own Modbus-TCP server is generated from.

    | Register | Path | Type | Role |
    |---|---|---|---|
    | 23 | `Ac/Out/L1/P` | int16, 10 W per count | Read: the Multi's own AC-out power, the compensation term |
    | 37 | `Hub4/L1/AcPowerSetpoint` | int16, W | Write: the control point (AC-input power target) |
    | 38 / 39 | `Hub4/DisableCharge` / `DisableFeedIn` | uint16 | Write: the two switches, plus both set after 30 s idle |
    | 800 | `Serial` | string[6] | Read: the GX device's own serial, once on connect — not a battery-pack serial, see below |
    | 840 | `Dc/Battery/Voltage` | uint16, V ×10 | Read: battery voltage, same block read as 842/843 |
    | 842 | `Dc/Battery/Power` | int16, W | Read: battery power, +charge/-discharge |
    | 843 | `Dc/Battery/Soc` | uint16, % | Read: battery SOC |
    | 2902 | `Settings/CGwacs/Hub4Mode` | uint16 | Read: the ESS-mode safety gate (`3` = External control) |

    Registers 37/38/39 are marked write-only in `attributes.csv`; the server's own source (`mappings.cpp`) shows its read path applies no such restriction, so reading them back (as one block) works regardless.

    **Why there's no cell voltage, temperature, or WiFi signal.** Per-cell min/max voltage and temperature exist in the official register map, but only on a *separate* `com.victronenergy.battery` D-Bus service with its own unit id — present only when the battery itself reports cell-level data to the GX device (e.g. BYD, Pylontech, Victron's own Lithium Smart), and absent on plenty of installations (this driver talks only to the `vebus` and `system` services, which never carry cell data). Inverter/heatsink temperature (`vebus` register 61, `Dc/0/Temperature`) exists but only populates when an optional Victron temperature sensor accessory is wired to the Multi, and its unpopulated-sensor behaviour hasn't been checked against real hardware — left out rather than guessed. WiFi signal strength isn't in the Modbus-TCP map at all, for any service: it's a Venus OS network-manager value that is never forwarded to Modbus-TCP.

    **Why the serial is the GX device's, not the battery's.** Register 800 lives on the `system` service — the same one already connected for battery power/SOC — so it costs nothing extra to read once on connect. It identifies the GX device (Cerbo GX, Venus GX, …), not the battery pack, since there's no separate per-battery service to read a pack serial from on an installation like the one above. It also keys the synthetic-energy backup, the same role a serial plays for every other driver: so a battery removed and re-added (after an IP change, say) reclaims its lifetime totals instead of starting over.

    **Why the Multi's own AC-out power, not a consumption figure.** `AcPowerSetpoint` targets the Multi's AC-*input*, not the battery: energy balance at the Multi is `AC_in = AC_out + battery_power`. A command that writes the desired battery power straight into the register only works when AC-out power happens to be zero — with any house load present, it asks for the wrong thing entirely (a "charge" intent can command a discharge). The `AC_out` term is read from the Multi's own measurement (`vebus` register 23), not from the GX device's derived figures. `Ac/Consumption/L1/Power` (817) can include load wired directly on AC-in, bypassing the Multi. `Ac/ConsumptionOnOutput/L1/Power` (878), which an earlier version used, is closer but is still a *consumption* figure: it adds back whatever AC-coupled solar on the output is serving and is never negative, so it stops matching what the Multi actually passes as soon as anything on the AC-out side generates — AC-coupled PV, or a second battery discharging on that circuit. Register 23 is signed and is exactly the term in the balance above; its only cost is 10 W resolution.

    **Why the setpoint follows the AC-out reading.** The Multi holds the last AC-input figure it was given, not the battery intent behind it. If AC-out power then moves and nothing rewrites the register, the battery silently covers the whole difference: a battery told to idle starts discharging when a load switches on, or charging when another source on the same circuit ramps up. Rewriting only when the *requested battery power* changes — as an earlier version did, with a periodic keepalive as the only other rewrite — therefore lets the battery drift for as long as the request stays the same. The driver now remembers the requested battery power itself and, on every fresh AC-out reading (about every 2 s), re-derives the AC-input figure and rewrites it if it changed.

    **Why idle uses the disable flags.** Matching the AC-input figure to AC-out power is not a true idle: the AC-out reading resolves only 10 W, and the Multi's own conversion losses come out of the battery, which showed as a steady 30-50 W discharge on real hardware. `DisableCharge` and `DisableFeedIn` are the same flags the GX device's own ESS uses to hold a battery idle; with both set the Multi cannot touch the battery at all. Omnibattery sets both once the command has stayed at 0 W for 30 seconds — not on every 0 W command, since the battery in use also passes through zero for seconds at a time and would flap the flags; the driver isn't told which battery the controller is using, and a lasting 0 W is how it tells — returns each to its switch's setting with the next non-zero command, corrects them if a readback disagrees, and drops the idle lock on unload. The two switches keep working alongside this: a flag is set when its switch is on *or* the battery is locked idle, and the switch shows your setting rather than the raw register. Switch settings are not stored and start off after a Home Assistant restart. If Home Assistant stops while the battery is idle the flags stay set until Omnibattery returns or you switch ESS Mode back, at which point the GX device manages them itself again.

    **Why the ESS-mode gate is fail-closed.** An early version of this check used `/SystemState/State` instead of `Hub4Mode`, and treated an unanswered check as "nothing to act on, proceed." On real hardware, that register returned a read error while `Hub4Mode` answered fine and read plain ESS, not External control — a permissive default would have written anyway, competing with Victron's own ESS algorithm for the same Multi. The gate now refuses whenever it cannot positively confirm `Hub4Mode == 3`; an unread or unreadable check is treated exactly like a confirmed-wrong one, never as permission.

    **Why a confirmed value still expires.** Confirming `Hub4Mode` or the AC-out power once and then caching it is not enough on its own: if that register's reads start silently failing afterwards — a Modbus hiccup, a GX-side restart of just that service — the driver would otherwise keep trusting a value that may no longer be true, indefinitely. Both carry the timestamp of their last successful read, and nothing is written once that timestamp is too old. Each has its own margin, about 5x its own polling cadence: 10 s for AC-out power (polled every ~2 s) and 150 s for `Hub4Mode` (polled every ~30 s). An earlier version shared one 60 s bound, which left `Hub4Mode` only 2x margin — a single ordinary missed poll could trip the gate, and that produced a write → passthrough → rewrite oscillation on real hardware (observed as the commanded power dropping to 0 and ramping back up every so often).

    **Why the rewrite doesn't wait for the fleet controller.** Even a correctly-held, unchanged setpoint must be rewritten periodically purely to satisfy the 60 s hardware watchdog, and the fleet controller only visits a given battery when it has something to (re)assert. A battery sitting inside the automatic controller's deadband — or blocked from discharging by a price rule — can go un-visited for far longer than 60 s, confirmed on real hardware: the official Victron GX integration's `State` sensor cycled Bulk/Passthru every 20-30 s with no matching Omnibattery log line. The rewrite therefore lives in the driver's own telemetry poll, alongside the AC-out tracking above: an unchanged setpoint is rewritten every 15 s, a changed one immediately. Nothing is written before the first command after a restart, or after Omnibattery is unloaded.

    **What a mock-based test suite can and can't prove.** The driver's unit tests use a fake Modbus client and prove the arithmetic and control-flow logic — clamping, the compensation formula, which refusal fires when. They cannot prove a given register answers on a given GX device, or that one register reports what its name implies versus a neighbouring one with a similar name. Both real bugs above were caught by running read-only checks against actual hardware, not by the test suite — which is also why automatic control has not yet been enabled on any real installation as of this writing.

    **What's still unverified:** the compensation formula itself has not been exercised with a live command against a real grid sensor (the recommended first test is a manual +200 W / -200 W step with the battery otherwise idle); the maximum simultaneous Modbus-TCP connections a GX device tolerates; and whether `Hub4Mode` is writable (only reading it is confirmed), which is why `standby()` cannot restore the GX device's own ESS mode and instead relies on the hardware's 60-second watchdog.
